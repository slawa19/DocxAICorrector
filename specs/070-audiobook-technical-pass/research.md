## R1. Эмодзи по свойствам Unicode (FR-005, Anti-regression 4)

**Решение.** Вендорить данные UTS #51 закреплённой версии в сгенерированный модуль `text/unicode_emoji_data.py` и
распознавать эмодзи-последовательности собственным сканером по грамматике UTS #51 (ED-14…ED-17). Версия данных —
**15.1.0**, ровно версия `unicodedata` рантайма: `wsl.exe -d Debian -- .venv/bin/python -I -c "import unicodedata;
print(unicodedata.unidata_version)"` → `15.1.0` (Python 3.13.5, проверено 2026-11-09). Источник —
`https://www.unicode.org/Public/15.1.0/ucd/emoji/emoji-data.txt`; генератор `scripts/generate-unicode-emoji-data.py`
читает локальную копию файла, пишет модуль с кортежами диапазонов `EMOJI`, `EMOJI_PRESENTATION`, `EMOJI_MODIFIER`,
`EMOJI_MODIFIER_BASE`, `EMOJI_COMPONENT`, `EXTENDED_PICTOGRAPHIC` и константами `UNICODE_EMOJI_DATA_VERSION = "15.1.0"`,
`UNICODE_EMOJI_DATA_SHA256 = "<sha256 исходного файла>"`. Генератор — инструмент разработчика (не рантайм, сети в
продукте нет); модуль коммитится.

Что удаляется (целой последовательностью, контракт — `data-model.md` §2):
- флаг: два `Regional_Indicator` подряд; тег-последовательность: база + `U+E0020…U+E007E`+ + `U+E007F`;
- keycap: `[0-9#*]` + необязательный `U+FE0F` + `U+20E3`;
- модификатор: `Emoji_Modifier_Base` + `Emoji_Modifier`;
- presentation-последовательность: символ `Emoji` + `U+FE0F`;
- символ с `Emoji_Presentation=Yes` сам по себе;
- ZWJ-цепочка: элемент (`U+200D` элемент)+, где элемент — любое из перечисленного или `Extended_Pictographic`.

Что НЕ удаляется глобально: `Emoji_Component` (цифры, `#`, `*`, ZWJ, `U+FE0F`, модификаторы вне последовательности),
комбинирующие знаки, символы с `Emoji=Yes` и `Emoji_Presentation=No` без `U+FE0F` (`©`, `™`, `↔`, `☺`) — они остаются
тексту; смысловые из них (`Sm`) ловит детектор FR-006.

Гард версии: тест `test_unicode_emoji_data_version_matches_runtime` — `UNICODE_EMOJI_DATA_VERSION ==
unicodedata.unidata_version`. Обновление Python до другой версии Unicode краснит тест, и данные перегенерируются той же
командой — категории `unicodedata` (детектор) и свойства эмодзи (чистка) не расходятся по версиям.

**Почему.** Стандартная библиотека не даёт свойств Emoji (`unicodedata` знает только категории). Это свойства стандарта,
не словарь книги (Codex, замечание 6). Модуль без зависимостей не меняет рантайм-окружение.

**Отвергнуто.**
- **Пакет `regex`** (`\p{Extended_Pictographic}`, `\X`). Его нет ни в `requirements.txt`, ни в `.venv`
  (`importlib.util.find_spec('regex') is None`; в `.venv/lib/python3.13/site-packages` пакета нет — 134 записи,
  проверено). Новая зависимость — установка в WSL и в образ CI (`scripts/docker-ci-parity.sh`); версия Unicode `regex`
  живёт своей жизнью и не совпадает с `unicodedata`; одного `\p{Extended_Pictographic}` мало (Codex 6) — грамматику
  последовательностей всё равно писать.
- **Пакет `emoji`** — база имён и псевдонимов (по сути словарь), тяжелее, релизный цикл не привязан к Unicode.
- **Чистка по категории `So`** — `№` это `So`, стрелки — `Sm` (Codex 6, проверено им через `unicodedata`); удалила бы
  смысловые знаки.

## R2. Где решается исключение абзаца и как отправляется смешанный блок (FR-003, FR-007)

**Решение.**
1. **Причина исключения вычисляется на документном слое**, в `document/semantic_blocks.build_editing_jobs`
   (`:274`), только когда `processing_operation == "audiobook"`: новое поле задания
   `narration_exclusion_reasons: list[str | None]`, параллельное `paragraph_ids` (`:343-346`), как уже параллельны
   `structural_roles` и `paragraph_regions` (`:351`, `:355`). Чистая функция `document/narration_exclusion.py::
   resolve_narration_exclusion_reason(...)` берёт роль (`_paragraph_structural_kind`, `:461`), регион
   (`_resolve_paragraph_regions`, `:906`), раздел заднего аппарата (`back_matter_sections`, `:289`) и форму текста.
   Словарь причин закрыт и живёт в `core/models.py` рядом с `PARAGRAPH_REGION_VALUES` (`:51-62`): `image`, `table`,
   `caption`, `toc`, `index`, `apparatus`, `notes_in_body`, `fragment`. Порядок приоритета фиксирован в этом же
   порядке (одна причина на абзац).
2. **Блок**: для `audiobook` `narration_include` блока = «есть хотя бы один абзац без причины»; блок без таких абзацев
   уже сегодня становится `passthrough` без вызова (`semantic_blocks.py:330-341`, условие `normalized_operation ==
   "audiobook" and not narration_include`).
3. **Отправка подмножества**: чистый `pipeline/audiobook_plan.py::build_audiobook_block_plan(payload)` разбирает
   `target_text_with_markers` по маркерам (форма `[[DOCX_PARA_id]]`, `generation/_generation.py:76`) и возвращает
   `send_ids`, `send_text_with_markers`, `send_text` и исключённые записи `(paragraph_id, reason, source_text)`. В
   `_generate_block_chunk` (`pipeline/block_execution.py:1235`) для `audiobook` в генератор уходят
   `target_text=plan.send_text_with_markers` и `expected_paragraph_ids=plan.send_ids` (сейчас — полные, `:1283`,
   `:1287`). Проверка маркеров генератора (`split_marker_preserved_paragraph_dispositions`, `_generation.py:828-907`)
   видит ровно отправленные ID — её не надо менять.
4. **Слияние**: `merge_audiobook_dispositions(plan, generated)` строит `MarkerPreservedBlockText` по ВСЕМ ID блока в
   исходном порядке; исключённые абзацы получают `ParagraphDisposition(status=policy_kept_source, text=<исходный
   текст>)`. Это прецедент 063 FR-011 / 064 FR-006 (`block_execution.py:515-539`, `:709-727`): статус «оставлено
   политикой» уже означает «в DOCX исходный текст, в озвучку не идёт, это не потеря» — проекция озвучки пропускает его
   без учёта в потерях (`:1540`), шлюз качества его не считает (`pipeline/quality_gate.py:516`), реестр его несёт.
   Причина исключения хранится не в статусе, а в записи исключения (`data-model.md` §1).

**Почему.** Только на документном слое известны роль и регион КАЖДОГО абзаца; после ответа модели — поздно (оплачено), а в
`state.narration_chunks` ID уже нет (`pipeline/narration_postprocess.py:482-486`). Вычисление только для `audiobook`
оставляет задания `translate`/`edit` побайтно прежними (SC-004 и кеш подготовки). Подмножество не трогает генератор и его
лестницу.

**Отвергнуто.**
- *Отправить весь блок и выбросить исключённое после ответа* — платим за оглавление и указатель, модель видит их как
  текст для озвучки и может склеить с соседом; спека прямо требует «модели НЕ отправляются».
- *Перерезать блоки на документном слое на озвучиваемые и нет* — меняет индексы блоков, контекст и ключ подготовки,
  расходится с заданиями перевода; радиус изменения больше нужного (Конституция VI).
- *Новый статус абзаца `narration_excluded`* — словарь статусов закрыт и сверяется при импорте
  (`_generation.py:341-348`, `PARAGRAPH_DISPOSITION_STATUSES`) и в отчёте; `policy_kept_source` уже несёт нужный смысл.
- *Исключать по региону `front_matter`* — Non-goal спеки (Codex 1–2).

## R3. Системный шаблон аудиокниги без изменения байтов перевода и редактуры (FR-004, SC-004)

**Решение.**
- Ранняя ветвь в `core/config.load_system_prompt` (`core/config.py:1751-1820`): если `operation.strip().lower() ==
  "audiobook"`, функция возвращает `_load_audiobook_system_prompt(prompt_variant)` ДО нормализации языков (`:1769`
  `… or "en"`), валидации (`:1773`) и интенсивности (`:1802`). Шаблон — новый файл
  `resources/prompts/system_prompt_audiobook.txt`; инструкции режима — `operation_audiobook.txt` (переписан), пример —
  `example_audiobook.txt` (переписан); вариант `repair` — `operation_audiobook_repair.txt`, без примера. В файлах нет
  плейсхолдеров `{…}`: шаблон собирается подстановкой двух секций по именам, без `str.format` языков. Аргументы
  `source_language`/`target_language`/`editorial_intensity`/`document_context_prompt` для этой ветви игнорируются —
  поэтому значения, оставшиеся в сессии от перевода, на промпт не влияют (FR-001, Edge Cases).
- `pipeline/support.build_system_prompt_arguments` (`pipeline/support.py:26-45`) для `audiobook` не читает
  `editorial_intensity_default` (`:35`) и отдаёт `source_language=""`, `target_language=""`, `editorial_intensity=""`
  (ключи остаются, потому что `resolve_system_prompt` (`:48`) требует их по имени); для `translate`/`edit` — без
  изменений. Контекст документа и глоссарий и так только для `translate` (`:12-23`).
- **Золотые тесты SC-004** (новый `tests/test_spec_070_request_golden.py`) записываются на `fdf775f` ДО любой правки
  (задача T-C1) и закрепляют обе общие точки сборки:
  1. SHA-256 строки `load_system_prompt(...)` для матрицы: операции `translate`, `edit`; варианты `default`,
     `toc_translate` (только translate), `literary_polish` (только translate); все интенсивности
     `_PROMPT_EDITORIAL_INTENSITY_PATHS`; пары `en→ru`, `auto→ru`, `ru→ru`, `de→en`; `document_context_prompt` `""` и
     одна фиксированная вымышленная строка;
  2. словари `build_system_prompt_arguments(context=…, prompt_variant=…)` на тех же осях (двойник контекста);
  3. запросы блока: в существующем `tests/test_generation_request_profile.py` (спека 069) случаи `translate` и `edit` не
     меняются; случай `audiobook` меняется НАМЕРЕННО в той же задаче WP-C (новый шаблон) — с записью в Changelog спеки.
  Тест пишется так, чтобы его можно было повторить на любой ветке: он не читает git.

**Почему.** Одна точка входа (`load_system_prompt`) для всех вызывающих; ветвь до нормализации — единственный способ не
изображать отсутствие пары фиктивной `en→ru` (Codex, таблица FR-001). Хеши — дешёвый и полный способ сказать «побайтно».

**Отвергнуто.**
- *Отдельная функция `load_audiobook_system_prompt` и выбор в каждом вызывающем* — вызывающих три (`_get_cached_system_prompt`
  `block_execution.py:1194`, вариант исправления, тесты), выбор размножается.
- *Оставить общий шаблон и «переопределить» правила 4–7 в промпте режима* — ровно нынешнее противоречие
  (`system_prompt.txt:46-52` против `operation_audiobook.txt:9`, `:28`).
- *Сравнивать промпты с файлами-эталонами* — эталон с текстом промпта пришлось бы обновлять каждой будущей спекой по
  переводу; хеш делает то же, а изменение видно по имени случая.

## R4. Что выдаёт операция `audiobook` после D-1 (решение по объёму)

**Решение. Набор файлов не меняется:** `.result.tts.txt` (основной), `.result.md` и `.result.docx`. DOCX и Markdown
содержат текст для озвучки по каждому озвучиваемому ID (после чистки и исправления) и исключённые абзацы в том виде, в
каком они пришли (`policy_kept_source`, R2). Экран результата (`ui/_ui.py:1166-1215`), bundle
(`processing/processing_runtime.py:1688`), запись артефактов и раннер не меняются, кроме удалений FR-002.

**Почему.** Минимальный объём (Конституция VI): удаление DOCX потребовало бы правок в сборке DOCX поздних фаз, экране
результата, раннере и проверках форматирования — ни одна из них не нужна для D-1…D-5. DOCX полезен проверяющему: адреса
`needs_review` указывают на абзацы, которые там видны вместе со структурой, а картинки и таблицы остаются на месте
(исключённые абзацы несут исходный текст и плейсхолдеры).

**Отвергнуто.** *Отдавать только `.tts.txt`* — шире объёма спеки, не требуется ни одним FR; при желании — отдельная спека.

## R5. Вызов исправления (FR-006, вызывающая часть)

**Решение.** Новый модуль `pipeline/audiobook_repair.py`, функция `repair_block_residue(...)` (контракт —
`data-model.md` §4, `contracts/prompts.md` §2):
- **Ровно один оплачиваемый вызов на блок**: `generation._generation.request_text_completion(client, request_kwargs,
  usage_stage="audiobook_repair")` (`generation/_generation.py:2467-2506`). Это путь вспомогательного вызова (так
  ходит глоссарий 063): `_call_responses_create` с `max_retries=1` и `retryable_error_predicate=lambda exc: False`
  (`:2038-2053`) — ни повторов, ни лестницы деградации, ни подстановки источника. Совместимый переход OpenRouter на Chat
  Completions (`:2500-2506`) случается только после ОТКАЗА Responses без генерации; снятие необязательного параметра
  (`image/shared.py:270-272`) — тоже отказ до генерации. Сгенерированный ответ — не больше одного.
- **Запрос**: `_build_request_kwargs(model=<модель FR-008>, system_prompt=load_system_prompt(operation="audiobook",
  prompt_variant="repair"), user_prompt=_build_marker_preserving_user_prompt(...), target_text=...)` (`:2372`, `:764`),
  без `request_profile` — как основной вызов аудиокниги (рассуждения нет). Цель — только абзацы блока с остатком, под их
  маркерами; контекст до — последний озвучиваемый абзац перед первым из них (итоговый текст, хвост ≤ 600 знаков),
  контекст после — первый озвучиваемый после последнего (≤ 600 знаков); границы блока не пересекаются.
- **Приём**: `split_marker_preserved_paragraph_dispositions(answer, expected_ids)` (`:828`) — бросает при отсутствии,
  дубле, перестановке маркеров, тексте до первого маркера и разрыве абзаца в многомаркерном ответе; любой абзац со
  статусом `retry_required` (пустой) — отказ. Отказ, исключение сети/SDK, `MarkerParagraphRecordLost` → прежний текст
  всех абзацев запроса, причина в счётчике и событии.
- **Stop**: `should_stop()` спрашивается ДО вызова; `True` → вызова нет, причина `stopped`, текст прежний; в сам вызов
  `should_stop` не передаётся (иначе `LatePhaseStopped` посреди обработки блока). Остановка прогона — обычная проверка
  между блоками.
- **Учёт**: константа `STAGE_AUDIOBOOK_REPAIR = "audiobook_repair"` в `core/model_accounting.py` рядом с `:81-94`.
  Стоимость пишется в точке учёта каждого ответа (`image/shared.py:232` — единая точка `responses.create`), значит и
  ответ, принятый провайдером и отвергнутый нами, учтён в долларах. Вызов, упавший без ответа, провайдер не тарифицировал и
  не прислал `usage` — он учитывается счётчиком `repair_failed_call_count` по причине, а не долларами (модуль учёта
  никогда не оценивает, `core/model_accounting.py:12-22`).
- После ответа (принятого или нет) — повтор FR-005, детектора и покрытия; второго исправления нет (вызывающий WP-G).

**Почему.** Спека требует «строго ОДИН оплачиваемый вызов API (без лестницы повторов и деградации основного генератора)»;
`generate_markdown_block` (`:3617`) — это и есть лестница (Codex 8). `request_text_completion` — уже существующий
однократный путь с тем же провайдером и учётом по стадии.

**Отвергнуто.**
- *`generate_markdown_block(..., allow_controlled_source_fallback=False)`* — нет подстановки источника, но остаются
  повторы попыток и восстановление пустого ответа (`_recover_from_persistent_empty_response`, `:2509`): до `max_retries`
  оплачиваемых вызовов.
- *Исправление после сборки `.tts.txt`* — ID уже нет (`narration_postprocess.py:482`).
- *Исправлять по абзацу отдельными вызовами* — N вызовов на блок вместо одного; спека — «один логический проход на блок».

## R6. Модель режима: один резолвер для UI и раннера (FR-008)

**Решение.** Новый модуль `core/audiobook_mode.py`:
`resolve_audiobook_model(app_config, *, requested_model: str | None, origin: str) -> AudiobookModelResolution(model,
source)`, где `source ∈ {"requested", "config"}`. Порядок: непустой `requested_model` → `app_config["audiobook_model"]`.
Второе уже равно `[models.audiobook].default`, а при его отсутствии — `[models.text].default`
(`core/config_runtime_sections.py:442-474`) и валидируется как `responses_text` (`core/config.py:1491-1496`); поэтому
три ступени FR-008 — это две ступени резолвера. DEBUG-событие `audiobook_model_resolved {origin, model, source}`.
- **Раннер**: `validation/profiles.py:309` (`model=run_profile.model or general_defaults.model`) для `audiobook` →
  `resolve_audiobook_model(app_config, requested_model=run_profile.model, origin=f"run_profile:{id}").model`.
- **UI**: селектор модели в «Дополнительно» для `audiobook` остаётся (спека говорит «явная модель UI»), но его значение
  по умолчанию — `resolve_audiobook_model(config, requested_model=None).model`, а «последний выбор» хранится в отдельных
  ключах сессии для `audiobook` (сейчас общий `_KEPT_MODEL_SELECTION_KEY`, `ui/_ui.py:261`, `:814-830`), чтобы выбор,
  сделанный в редактуре, не протекал в аудиокнигу. Выбранное значение передаётся как `requested_model`.
- **Исправление** берёт тот же клиент и тот же ID модели, что и основной вызов блока (`initialization.text_client`,
  `context.model_id or initialization.text_model_id or context.model`, `block_execution.py:1246-1247`).

## R7. Пустой ответ, `source_restored`, controlled fallback в аудиокниге (FR-001, FR-003, Edge Cases)

**Решение.** После исключения `audiobook` из `LANGUAGE_CHANGING_OPERATIONS` (`core/models.py:37`) исходный текст абзаца —
это текст на языке книги. Поэтому в аудиокниге:
- `omitted` (пустой ответ на последней попытке; генератор уже кладёт исходный текст, `_generation.py:1160-1163`) —
  ОЗВУЧИВАЕТСЯ исходным текстом, `needs_review` с причиной `empty_answer`;
- `source_restored` (`:1139-1145`) — озвучивается, `needs_review` с причиной `source_restored`;
- controlled fallback блока (исходный текст всего блока, `block_execution.py:2029-2060`) — каждый озвучиваемый абзац
  блока озвучивается исходным текстом, `needs_review` с причиной `source_fallback`;
- все три проходят FR-005, детектор и ОДНО исправление, как обычный ответ (исходный текст тоже может нести цифры).
Повторы основного генератора при пустом ответе остаются (бюджет попыток — как сейчас); меняется только итог.

Следствие: семьи потерь озвучки `narration_excluded_source_fallback_*` и `narration_excluded_omitted_*`
(`pipeline/contracts.py:275-297`), события `narration_source_fallback_excluded` / `narration_omitted_paragraphs_excluded`
(`pipeline/late_phases.py:1299-1333`), их notices и разбор в `quality_gate.build_narration_exclusion_facts`
(`pipeline/quality_gate.py:2491`) теряют единственного производителя — перевод и редактура больше не озвучивают
(FR-002), а аудиокнига больше не исключает «чужой язык». Они удаляются (правило владельца «убирать мёртвые оси»),
вместо них — записи `needs_review` (`data-model.md` §5).

**Почему.** Edge Cases спеки: «Модель вернула ПУСТОЙ текст … абзац получает исходный текст и пометку `needs_review`»,
«Модель вернула абзац без изменений — это правильный текст, он озвучивается». Удаление `audiobook` из множества само по
себе разрешает `source_restored`, но не `omitted` (Codex 4): `withheld_statuses` для неязыковых операций всё ещё
`{omitted}` (`block_execution.py:1529-1533`).

**Отвергнуто.** *Оставить семьи потерь со значением 0* — мёртвые поля в отчёте и логе.

## R8. Сборка по ID и чистка вместо разбора Markdown (FR-005, FR-007)

**Решение.**
- **Чистка одного абзаца** — чистая функция `text/narration_cleanup.py::clean_narration_paragraph(text) ->
  CleanupResult(text, stats)`, порядок: (1) внутренние токены конвейера `[[DOCX_<KIND>_…]]` (форма
  `_generation.py:86`) — снимаются (маркеры абзацев разобраны раньше, по ним текст и пришёл; см. О-9 плана);
  (2) HTML по синтаксису тега: `<имя …>`, `</имя>`, `<имя/>`, где имя — `[A-Za-z][A-Za-z0-9-]*`; `<br>` и блочные теги
  (`p`, `div`, `li`, `tr`, `td`, `th`, `table`, `ul`, `ol`, `h1`–`h6`, `blockquote`) → пробел; строчные → ничего;
  содержимое остаётся; сущности — `html.unescape`; одиночный `<` без имени элемента (`a < b`) не трогается;
  (3) эмодзи — R1; (4) разметка Markdown, которую модель вернула вопреки промпту: префикс заголовка `#{1,6}`, префикс
  цитаты `>`, маркер списка `[-*+]` и глиф-украшение в начале строки (категория `So`/`Sm` или глиф маркера списка
  `●•◦‣`, отдельным токеном с разделителем после — FR-005, как `_generation.py:91-104`, но БЕЗ `\d+\.\s+`), выделение
  `**`/`__`/`*`/`_` (`:111-112`), обратные кавычки, ссылка `[текст](адрес)` → `текст`; (5) схлопывание пробелов.
  Сырой URL кодом больше не удаляется (сейчас `_generation.py:604`): по FR-005 «всё прочее переписывает модель» — его
  ловит класс детектора «URL и домены». Квадратные скобки с текстом не трогаются (Anti-regression 5).
- **Сборка `.tts.txt` по записям**: `state.narration_paragraphs` — список записей
  `NarrationParagraphRecord(paragraph_id, block_index, role, text, needs_review_reasons)` в порядке блоков и абзацев;
  итог — тексты записей через `"\n\n"`. Детерминированная склейка разорванного предложения
  (`_narration_paragraph_continues`, `_generation.py:626-671`) сохраняется по ФОРМЕ (хвост не на `.!?…:;`, не на
  закрывающей кавычке и не на цифре; голова — строчная буква), но «вид абзаца» берётся из роли подготовки
  (`payload.structural_roles`, `semantic_blocks.py:351`): склеиваются только два абзаца роли `body`. Каждая склейка
  записывается парой `(prev_id, next_id)`; это отдельный счётчик, не «склейка модели».
- Старая цепочка `strip_markdown_for_narration*` / `_narration_paragraphs` / `_join_narration_sentence_continuations` и
  константы `_NARRATION_*` (`_generation.py:86-123`, `:533-698`) удаляются вместе с последним вызывающим
  (`narration_postprocess.py:135`, `:205`); их поведенческие тесты (`tests/test_narration_markdown.py`) переносятся на
  `clean_narration_paragraph` и сборку по записям — те случаи, что остаются верными, сохраняются дословно.

**Почему.** FR-007: «сборка по ID и роли из подготовки, а не по возвращённому Markdown»; новый промпт велит Markdown не
возвращать, и «вид» по Markdown держался на непослушании модели (REVIEW «Ответы», п. 1). Склейка после снятия маркеров
заменяла границу абзаца пробелом и делала SC-003 непроверяемым (Codex 5).

**Отвергнуто.** *Оставить разбор по Markdown и запретить склейку* — теряем 81 из 83 починок импортных разрывов
(`_generation.py:631-636`); *склеивать по Markdown-виду* — вид исчезнет вместе с Markdown.

## R9. Сигнал покрытия по абзацу (FR-007)

**Решение.** `text/narration_coverage.py::paragraph_coverage(source, answer) -> CoverageResult(long_word_count,
found_count, ratio | None)`: «длинное слово» — непрерывная последовательность букв (`[^\W\d_]+`) длиной ≥ 6; сравнение по
основе — первые 5 букв после `casefold`; слова входа ищутся среди основ ОТВЕТА ЭТОГО ЖЕ абзаца. Цифры не буквы — число
словами в ответе не уменьшает долю, цифра во входе не считается (это и есть «после удаления цифр с обеих сторон»).
Сигнал не меряется (`ratio = None`, счётчик `coverage_not_measured`), если во входе < 4 длинных слов или < 6 токенов через
пробел (порог спеки 065 FR-005, `_generation.py:177`, — для письма без пробелов доля по буквам смысла не имеет). Порог
`needs_review` — `ratio < 0.6`; **предварительный**: это порог `loss.py` (`D:\Temp\docxai-research\audiobook-review\loss.py:14`),
под которым на двух старых прогонах не оказалось ни одного абзаца (Codex 10: 0 из 87/88) — откалибровать по
ложным срабатываниям нечем, это делает FR-009 чтением каждого срабатывания.

**Почему.** Спека задаёт форму сигнала («доля длинных слов абзаца входа в ЕГО ответе»), но не числа; повторить формулу
измерителя, по которому сделан раздел «Что измерено», — единственная ссылка, которая есть.

**Отвергнуто.** *Отношение длин* (REVIEW №10) — число словами удлиняет ответ, сигнал шумит именно там, где режим работает.

## R10. Правило обрывка и роли, которые оно не трогает (FR-003; отклонение О-1 плана)

**Решение.** `document/narration_exclusion.py::is_fragment_without_connected_text(text) -> bool` — ровно форма спеки:
нет ни одного буквенного токена (`[^\W\d_]+`) из ≥ 3 букв, ЛИБО буквы составляют < 1/2 непробельных знаков. Правило НЕ
применяется к абзацам с ролью подготовки `heading`, `epigraph`, `attribution`, `dedication` (О-1).

**Почему.** Спека требует и правило обрывка «во всём документе», и «заголовки, эпиграфы и атрибуции озвучиваются». Буквально
применённое правило исключает заголовок «III» или «1», атрибуцию «— Ю. Ли» (нет токена из трёх букв) — это и есть
противоречие внутри FR-003. Роль — сигнал подготовки (Конституция VII разрешает), не форма текста.

**Отвергнуто.** *Применять правило ко всему* — теряем номера глав и короткие атрибуции; *исключение по длине* —
Конституция VII. Цена выбора: OCR-мусор, которому импорт присвоил роль `heading`, звучит; детектор FR-006 покажет его
(римские, цифры) и SC-001 требует прочитать каждое срабатывание и каждый такой случай.

## R11. Абзацы-примечания в теле (спека 067) как аппарат (FR-003; отклонение О-2 плана)

**Отвергнуто.** *Только регион* — буквальное прочтение FR-003; оставлено как запасной вариант, если оркестратор не
подтвердит.
