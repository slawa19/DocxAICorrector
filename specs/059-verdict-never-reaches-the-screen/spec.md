# Часть A. Причина: почему проза теряется — и почему это исправимо до нуля

## A-1. Сегодня теряют ОБА пути, разными способами

**Путь документа: доставлен английский исходник.** Когда модель не дала принятого ответа даже после
recovery, генератор возвращает исходный текст блока (`_generation.py:2013-2091`, четыре ветки). Текст
на месте, перевода нет.

**Путь озвучки: текста нет вообще.** Это не «не пускается», это **выбрасывается**:

```
block_execution.py:976-995
    if not payload.narration_include:
        state.excluded_narration_block_count += 1
    elif fallback_delivered_source_text(payload=payload, processed_chunk=processed_chunk):
        narration_excluded_by_source_fallback = True
        state.narration_excluded_source_fallback_block_count += 1     # :980
        state.narration_excluded_source_fallback_chars += len(...)    # :981
    else:
        ...
        state.narration_chunks.append(narratable_text)                # :995 — ЕДИНСТВЕННЫЙ append
```

В ветке подстановки (`:978-981`) в `state.narration_chunks` не добавляется ничего. На прогоне
2026-08-06 Money & Sustainability из аудиокниги **пропало 5 581 символов** — не прозвучало
по-английски, а не прозвучало вовсе
(`artifacts/audiobook_final_run/money_sustainability/run_summary.txt:52-53`).

**И это дыра именно в ПРОЗЕ, а не в законно вырезанном.** Законные исключения считаются отдельно и
работают: `narration_excluded_blocks=59` (`:51`) — это `_resolve_narration_include`
(`document/semantic_blocks.py:786-803`), который выбрасывает TOC-блоки, блоки-картинки, пустые и блоки
из региона back-matter. 5 581 символ идут **сверх** этих 59 блоков.

**Отсюда — переоценка комментария `block_execution.py:965-974.`** Он объясняет асимметрию так:
документ редактируем, человек починит непереведённый абзац, а между звуком и слушателем никого нет.
Рассуждение честное, но оно выбирало **между двумя способами потерять** — отдать английский или
выбросить, — а не между потерей и переводом. По мерке владельца оба исхода критические, и оправданием
асимметрия больше не является. Что в комментарии остаётся верным и переносится дальше: **брать
отвергнутый вывод модели нельзя** — отказ означает, что модель могла ПОТЕРЯТЬ абзац, и это меняет
видимый дефект на непроверяемый.

## A-2. `marker_validation_source_fallback` — отказ ПАКЕТИРОВАНИЯ, а не отказ перевода

Ключевое различение, и оно доказывается кодом.

**Маркеры — это надстройка, а не режим работы переводчика.** `enable_paragraph_markers` по умолчанию
**False** (`core/config_runtime_sections.py:541`); они включаются поверх, на конкретный прогон
(`runtime_overrides={"enable_paragraph_markers": true, …}` —
`audiobook_final_run/money_sustainability/run_summary.txt:20` и `money_translate_docx:20`, оба
2026-08-06). `marker_mode` — обычный булев параметр, протянутый через весь путь генерации:
`generate_markdown_block(..., marker_mode: bool = False, ...)` (`_generation.py:1852`).

**При `marker_mode=False` весь класс ошибки недостижим — по коду, а не по обещанию:**

- `_strip_and_validate_paragraph_markers` возвращает ответ нетронутым: `if not marker_mode: return
  markdown` (`:1035-1040`);
- `_strip_paragraph_markers_from_source` — тоже: `if not marker_mode: return target_text`
  (`:1022-1023`);
- `_deliver_marker_preserved_block` не требует записи: `if not marker_mode: return value` (`:236-237`);
- промпт берётся другой — `_build_standard_user_prompt` вместо `_build_marker_preserving_user_prompt`
  (`:1888-1900`).

`paragraph_marker_validation_failed` возбуждается только внутри маркерной ветки, поэтому при N=1 без
маркеров сопоставление «один вход — один выход» тривиально по построению, и ошибка не может
возникнуть. **Контракт маркеров существует, чтобы сопоставить N абзацев за ОДИН вызов. Если
сопоставление не удалось — надо убрать пакетирование для этого блока, а не отдавать исходник.**

## A-3. Ступенчатая деградация: требование, и что мешает каждой ступени сегодня

### Ступень 1 — как сейчас

Блок с маркерами, пакетно, быстро. Без изменений. Ретраи с адресными лекарствами (`:1967-1973`).

### Ступень 2 — блок отвергнут → повторить абзацы ПООДИНОЧКЕ, без маркеров

Точка встраивания: там, где сейчас стоят ветки подстановки, `_generation.py:2013-2091`, **до** любой
из них.

**Что уже есть в области видимости в этой самой точке** — ничего нового прокладывать не надо:
`client`, `model`, `system_prompt`, `max_retries` (параметры функции, `:1843-1853`);
`source_paragraph_chunks` — по одному куску ИСХОДНОГО текста на каждый `paragraph_id`, уже нарезанные
(`:1907-1911` через `_split_marker_preserved_markdown:857`); `context_before_text` /
`context_after_text` (`:1870-1871`); `expected_paragraph_ids`.

**Что мешает — три конкретные вещи, и ни одна не является препятствием по существу:**

1. **Нет повторного входа.** Все четыре ветки подстановки `return`-ят строку; ни одна не вызывает
   `generate_markdown_block` заново для подмножества. Функция сегодня не рекурсивна — это то, что надо
   написать, и это единственное настоящее изменение потока.
2. **Контракт возврата в маркерном режиме.** `_deliver_marker_preserved_block` (`:222-242`) возбуждает
   `MarkerParagraphRecordLost`, если возвращаемая строка не несёт пер-абзацной записи. Значит
   результаты одиночных вызовов нельзя просто склеить — надо собрать запись. **Примитив для этого уже
   существует**: `_marker_preserved_block_text` (`:207-219`) строит текст ИЗ записи, а
   `_block_source_fallback_result` (`:1732-1745`) уже делает ровно эту сборку — только со статусом
   `source_restored`. Ступень 2 делает то же самое со статусом `accepted`.
3. **Ошибка не называет, КАКОЙ абзац виноват, для всех кодов.** `MarkerValidationError` несёт
   `expected_paragraph_ids` и `found_paragraph_ids` (`:263-264`), чего хватает для ошибок
   идентичности/порядка, но `empty_marker_chunk` и `unexpected_prefix` не выносят наружу конкретный
   индекс. **Честное простое правило: при любом отказе маркерного контракта переспросить ПОИМЁННО ВСЕ
   абзацы блока.** Ограничено, детерминировано, не требует новой диагностики.

**Цена, посчитанная, а не оценённая на глаз.** Прогон 2026-08-06 money_sustainability:
`retried_paragraph_count=67` при `retried_block_count=12` (`:42-43`; счётчик суммируется один раз на
блок, `core/model_accounting.py:287-289`) → **5,58 абзаца на отвергнутый блок**. До подстановки дошли
2 блока → **≈11 дополнительных вызовов** против 307 вызовов прогона за 0,513555 $ (`:48`). Даже по
средней цене вызова это **≤ 0,02 $, менее 4% стоимости прогона** — а одиночный вызов дешевле среднего,
потому что несёт меньше контекста.

### Ступень 3 — `incomplete_response` → делить, а не подставлять

Это отказ **по размеру**, и это доказуемо: `_boost_request_output_budget` (`:1607-1618`) удваивает
`max_output_tokens` с полом 1024 на ретрае (`:97`, `:1968-1971`) и 1536 на recovery (`:98`,
`:1994-1998`) — **но с потолком 16 384** (`:1616`, `:1618`). Блок, чей перевод не помещается в
потолок, не будет отвечен целиком никогда, сколько ни повторяй.

`_can_fallback_to_source_text_after_incomplete_response` (`:1752-1753`) — это `bool(target_text.strip())`.
Он не смотрит на размер, не сравнивает с бюджетом и не выбирает между подстановкой и делением: он
отвечает только на вопрос «есть ли вообще исходный текст, который можно вернуть». **Ничто в нём не
мешает делить — там просто нет соответствующего решения.**

**Что мешает делению, конкретно:**

1. То же отсутствие повторного входа (пункт 1 выше).
2. **Ниже одного абзаца маркера нет.** При делении по предложениям куски надо склеить обратно в текст
   ЭТОГО абзаца до сборки записи. Это текстовая операция, а не изменение контракта: маркер не
   создаётся и не уничтожается, число абзацев инвариантно по построению. Выше одного абзаца деление —
   это в точности ступень 2.

Живая частота: 1 блок за прогон, на `translate` (`money_translate_docx/run_summary.txt:45,47`,
2026-08-06). Приоритет второй, но исход тот же — перевод, а не подстановка.

### Ступень 4 — тот же абзац ДРУГОЙ моделью

Убивает отказ, специфичный для модели. `english_residual_output`
(`pipeline/output_validation.py:329-330`, предикат `has_unexplained_english_residuals:363`) означает,
что ЭТА модель на ЭТОМ тексте упорно отвечает на языке источника. Это свойство конкретной модели, а не
текста, и другая модель его не разделяет. Дефолт —
`openrouter:google/gemini-3.1-flash-lite-preview` (`src/docxaicorrector/resources/config.toml:91`), то
есть самая маленькая и дешёвая из шести перечисленных в `[models.text].options` (`:92-99`); именно её
профиль и даёт этот класс отказа.

**Обвязка почти вся уже есть, и это три проверенных факта:**

- `generate_markdown_block` принимает клиента и модель обычными параметрами
  (`_generation.py:1843-1846`) — переключение модели на один вызов не требует ничего менять внутри
  генератора;
- фабрика клиента по селектору **уже висит на объекте зависимостей пайплайна**:
  `get_client_for_model_selector: ModelSelectorClientFactory` (`pipeline/contracts.py:211`, прокладка
  `:360`, `:381`, `pipeline/setup.py:293`, `:301`);
- **рабочий прецедент ровно этого приёма уже есть**: `narration_postprocess.py:341-352` резолвит
  ДРУГОЙ селектор в клиента через `_resolve_text_call_target`
  (`pipeline/text_call_support.py:15-29`), а `:400-409` вызывает
  `dependencies.generate_markdown_block(client=…, model=model_id, …, marker_mode=False)`. То же самое
  делает `reader_cleanup_postprocess.py:263`, а `document/boundary_review.py:183-185` зовёт
  `get_client_for_model_selector(model, "responses_text")` напрямую.

**Что мешает — три вещи, названные конкретно:**

1. **Слой.** Ступени 2 и 3 живут внутри генератора, а фабрика клиента — на `dependencies`, до которой
   генератор не дотягивается: он получает `client` и `model` уже готовыми. Значит ступень 4 должна
   стоять НЕ внутри `_generation.py`, а на вызывающей стороне — `block_execution.py:453`, где
   `dependencies` в области видимости. Это и архитектурно правильно: ступень 4 пересекает границу
   провайдера, ступени 2-3 — нет.
2. **Селектор эскалации нигде не назван.** `[models.text].options` перечисляет кандидатов, но не
   говорит, НА ЧТО эскалировать. Нужен один закреплённый ключ конфигурации — по образцу уже
   существующих `reader_cleanup_model` / `reader_verifier_model` (`resources/config.toml:74-75`),
   которые закреплены за ролью именно так, с объяснением, почему их нельзя менять походя.
3. **Ключ провайдера может быть не настроен.** `get_client_for_model_selector`
   (`core/config.py:1635-1654`) идёт в `get_provider_client`, который возбуждает `RuntimeError`, если
   провайдер выключен или не сконфигурирован (`:1559-1565`). Дефолт ходит через OpenRouter, а
   `anthropic:claude-sonnet-4-6` требует другого ключа. Ненастроенный провайдер эскалации — это
   **состояние конфигурации**, обязанное быть названным своим именем, а не молча превращаться в
   подстановку исходника.

**После четырёх ступеней состояния «этот абзац нельзя перевести» не существует.**

## A-4. Гарантия: доставка непереведённой прозы становится НЕВЫРАЗИМОЙ

Лестница делает отказ недостижимым. Инвариант делает плохой исход невыразимым — и механизм для него
уже есть в архитектуре, просто отказы перевода к нему не подключены.

`CONTROLLED_BLOCK_FAILURE_POLICY` (`pipeline/block_execution.py:20-38`) уже делит отказы на два
решения. Сегодня **все семь** отказов по качеству текста — `fallback_continue` (подставить исходник и
идти дальше): `empty`, `empty_processed_block`, `source_text_fallback`, `english_residual_output`,
`heading_only_output`, `bullet_heading_output`, `toc_body_concat` (`:21-27`). И **десять** структурных
отказов — уже `fail`: `missing_provider_client`, `missing_provider_configuration`,
`missing_source_segment`, `missing_translated_segment`, `final_translated_book_incomplete`,
`marker_registry_failure`, `marker_anchor_failure`, `invalid_processing_job`, `corrupted_block`,
`source_extraction_failure` (`:28-37`).

**У таблицы ровно один потребитель** — `classify_processed_block_failure_decision` (`:140-167`, чтение
таблицы на `:148`), вызываемый из одного места (`:1163`). Узкая горловина: инвариант ставится в одну
точку, а не рассыпается по обработчикам.

**Требование.** Для абзаца ПРОЗЫ (по регионам из A-6) исходы, оставляющие текст непереведённым,
перестают быть `fallback_continue`. Они обязаны эскалировать по лестнице; исчерпание лестницы даёт
`fail`. Для аппарата (сноски, оглавление, индекс) `fallback_continue` остаётся законным — владелец
сказал, что они не в счёт.

Формулируется это как **инвариант, а не как обработчик**: доставка документа с непереведённой прозой
перестаёт быть выразимым исходом. Пользователь получает либо полный перевод, либо явный отказ с
указанием абзаца — но не книгу с английскими заплатками.

**Побочная находка, которую надо назвать.** У `fallback_continue` на уровне пайплайна **нет
run-level счётчика**: `continue_controlled_processed_block_rejection` пишет артефакт и статус
(`block_execution.py:956`, `:1024`, `:1039`), а `model_output_discarded_reason_counts` в
`run_summary.txt` наполняется только из генератора (`_generation.py:985`, `:2014`, `:2033`, `:2052`,
`:2077`). Поэтому по записанным артефактам **нельзя сказать, сколько раз сработали
`english_residual_output`, `heading_only_output` и `toc_body_concat`** — в `artifacts/` этих имён нет
ни разу. Это неизмеряемый путь потери, и инвариант закрывает его заодно.

## A-5. Честный остаток: недоступность провайдера — и это не «не смогли перевести»

После четырёх ступеней остаётся ровно одно: **недоступность провайдера** — сеть, лимиты, 5xx, отказ
модели отвечать после всех повторов на всех ступенях. Тогда прогон падает.

**Это не «мы не смогли перевести абзац», это «прогона не было»** — состояние видимое, отличимое и не
выдающее себя за успех. Лечится повторами с отступом (`_generation.py:1974` уже делает
`time.sleep(min(2 ** (attempt - 1), 8))`), а не подстановкой.

**Машинерия для громкого падения уже есть и работает.** Если предикаты подстановки не срабатывают,
генератор доходит до `raise last_exception` (`:2093`); `process_single_block`
(`block_execution.py:1137-1148`) уходит в `handle_block_generation_failure`
(`pipeline/block_failures.py:82`), который выставляет `latest_docx_bytes=None` (`:119`, `:139`), пишет
`error_code="block_failed"` (`:121`) и вызывает `emit_failed_result_fn` (`:150`). Сегодня этот путь
обходится подстановкой; под новым требованием он становится правильным адресатом.

**Ноль достижим.** Недостижима стопроцентная доступность чужого API — и это утверждение о другой
величине.

## A-6. Что считается ПРОЗОЙ — по региону, а не по форме текста

Владелец: сноски и оглавление не в счёт, остальное — да. Детектор по форме изобретать запрещено
(Конституция VII), и не нужно: детекция по РЕГИОНУ в проекте уже есть, с обеих сторон.

## A-7. Требования части A

**FR-A1 (главное). Ноль абзацев ПРОЗЫ доставлено на языке источника, и ноль абзацев прозы
отсутствует в озвучке.** Оба пути, одно требование. Подстановка исходника и выбрасывание из

**FR-A2. Ступень 2 реализуется в `_generation.py`, до веток подстановки (`:2013`).** При отказе
маркерного контракта — переспросить все абзацы блока поодиночке с `marker_mode=False`; собрать

статусом `accepted` для переведённых. Соседний контекст передаётся из соседних кусков
`source_paragraph_chunks`, а не выбрасывается.

**FR-A3. Ступень 3: `incomplete_response` лечится делением, а не подстановкой.** Делить до одного
абзаца, при необходимости — по предложениям с обратной склейкой в текст того же абзаца. Потолок

обойтись нельзя.

**FR-A4. Ступень 4: тот же абзац другой моделью, на вызывающей стороне.** Реализуется в
`block_execution.py` рядом с `:453` — там, где `dependencies` в области видимости, — по образцу
`narration_postprocess.py:341-352` + `:400-409` через `_resolve_text_call_target`
(`text_call_support.py:15-29`). Селектор эскалации закрепляется отдельным ключом конфигурации по

**FR-A5 (инвариант). Доставка непереведённой прозы — невыразимый исход.** В

   одним рендерером** (`processing_runtime.py:170`, `runtime/state.py:635`, `:764`, тесты
   `tests/test_processing_runtime.py:254-280`, `tests/test_document_pipeline_output_validation.py:2552`,
   `:2735`, `:2789`). Пользователю бесполезен: в доставленном DOCX блоков нет.
2. **Идентификаторы абзацев — точный адрес, уже вычисленный.** `_block_source_fallback_result`
   (`_generation.py:1706-1745`) строит по одному
   `ParagraphDisposition(paragraph_id=…, status=PARAGRAPH_STATUS_SOURCE_RESTORED)` на абзац; пайплайн
   читает это обратно через `marker_paragraph_dispositions(processed_chunk)` — ровно так работает
   фильтр озвучки (`block_execution.py:647-655`). **Список подставленных абзацев известен поимённо
   уже сегодня.**
3. **Учёт по статусам есть, адреса в нём нет.** `record_paragraph_disposition`
   (`core/model_accounting.py:297-306`) считает количества; `paragraph_disposition_counts` (`:350`) —
   четыре числа.

**Чем адресовать — предложение.** Использовать существующий механизм ревью-элементов:
`_build_formatting_review_item` (`quality_gate.py:581-606`) даёт `reason`, `label`, `severity` и
`sample` с **якорем** — куском текста для Ctrl+F в DOCX. Механизм уже очищает якорь от внутренних
идентификаторов (`:597-599`, «internal ids must never reach the user-facing anchor» — значит
`[[DOCX_PARA_…]]` не утечёт), помечает `anchor_usable=False`, когда искать нечего (`:602-606`), умеет
печататься в скачиваемый файл (`runtime/artifacts.py:274-330`) и рисоваться на экране
(`_ui.py:801-838`).

**Цена.** Новых артефактов и путей рендеринга не нужно. Единственное препятствие — то же, о чём вся
часть B: `formatting_review_items` доезжают до экрана только при `quality_status` = `warn`/`fail`
(`quality_gate.py:1996`). Находимость чинится тем же изменением границы.

**Пометку в самом DOCX отвергаю.** Любая вставка означает, что человек обязан её потом убрать руками —
ДОБАВЛЯЕТ ручную правку, тогда как мерило владельца её вычитает. Плюс `no_placeholder_markup` —
приёмочная проверка (`validation/acceptance.py:450-467`), и на всех прогонах
`output_contains_placeholder_markup=False` (`money_sustainability:69`, `money_translate_docx:60`).
Якорь во внешнем отчёте даёт ту же находимость и не трогает продукт.

## B-4. Требования части B

**FR-B1.** Производственный вердикт пересекает границу как ДАННЫЕ: `passed` и `failed_checks` из
`quality_report["acceptance_verdict"]` доезжают до состояния UI. UI не импортирует
`validation.acceptance` и не пересчитывает вердикт (образец — `ui/review_presentation.py:3-9`).

**FR-B2.** Красный вердикт виден в любом режиме, в частности в `edit` и `audiobook`. Триггер —
`acceptance_verdict.passed is False`.

**FR-B3.** Экран называет проваленные проверки словами, по которым можно действовать. Имена проверок —
закрытое перечисление, принадлежащее `validation/acceptance.py`: структурный факт, а не литерал из
книги. Запись в обоих каталогах локалей, проверенная гардом, который видит выбранную схему именования.

**FR-B4.** Тревога о непереведённой прозе не зависит от режима: условие `narration_text is not None`
(`late_phases.py:1178`, `:1213`) перестаёт управлять фактом DOCX. Это два разных факта — «в документ
доставлен исходный текст» и «блок исключён из озвучки»; счётчик с префиксом `narration_excluded_*` на
прогоне `translate` называет себя неправдой, исправить надо и имя, и условие.

**FR-B5 (находимость).** На каждый подставленный абзац — ревью-элемент с якорем по образцу
`_build_formatting_review_item:581-606`; источник — `marker_paragraph_dispositions(processed_chunk)`.
Результат: человек делает Ctrl+F, а не перечитывает книгу. Абзац без пригодного якоря считается, а не
печатается пустой строкой (`:602-606`) — адрес не выдумывается (Конституция VII).

**FR-B6.** `latest_controlled_block_fallback_artifact` либо начинает читаться, либо удаляется вместе
со своими тестами.

**FR-B7.** Отбрасывание уведомления перестаёт быть молчаливым: белый список `_ui.py:863` расширяется,
и в нём, и в `:874-875`, `:876-877`, `:884-885` отбрасывание сопровождается WARNING с `kind` и
`message_key` (Конституция V).

**FR-B8.** Вердикт на экране — ревью-данные, а не гейт доставки: новая причина не блокирует выдачу и
не меняет `delivery_disposition` (Конституция VII «no verifier as a gate», спека 010). Блокирует
по-прежнему только `caption_heading_conflict` (`quality_gate.py:1691-1697`). **Это не противоречит
FR-A5:** невыразимость плохого исхода обеспечивается решением `fail` в
`CONTROLLED_BLOCK_FAILURE_POLICY` и падением по пути `block_failures.py:82-160` — на стороне
пайплайна, а не превращением экранного вердикта в гейт. Часть B сообщает о том, что уже случилось,
она ничего не запрещает.

## Anti-regression

### Часть A

1. **Ноль абзацев ПРОЗЫ доставлено на языке источника.** Прямая проверка по регионам A-6 над
   доставленным DOCX. **Анти-вакуум: проверка обязана уметь падать, и сегодня она падает** — на
   `artifacts/audiobook_final_run/money_sustainability/run_summary.txt` (2026-08-06) она поймала бы
   2 блока / 5 581 символ (`:45,47,52-53`), на `money_translate_docx` — 1 блок (`:45,47`). Проверка,
   зелёная на этих двух прогонах, сломана.
2. **Ноль абзацев ПРОЗЫ отсутствует в озвучке относительно доставленного документа.** Это ПРЯМАЯ
   проверка дыры, которой сейчас нет вовсе: сегодня `narration_excluded_source_fallback_*` считает
   выброшенное, но никто не сверяет озвучку с документом. Легальные исключения (TOC, картинки,
   back-matter — `semantic_blocks.py:786-803`) вычитаются по региону, а не по счётчику; на
   2026-08-06 это 59 блоков (`:51`), и они остаются законными.
3. **Объём доставленного текста не падает.** Правило, которое просто перестаёт подставлять исходник, —
   это потеря, а не починка. Контроль: доставленные символы не уменьшились, `narration_char_count` не
   ниже 456 612 (`:49`), а в `paragraph_disposition_counts` (`core/model_accounting.py:350`) растёт
   `accepted` за счёт `source_restored`, а НЕ за счёт `omitted`.
4. **Цена ограничена и измеряется.** `model_call_count` растёт не более чем на число абзацев
   отказавших блоков (на 2026-08-06 — ≈11 из 307, `:48`). Взрывной рост означает, что ступень 2
   включается там, где не должна.
5. **Отвергнутый вывод модели не доставляется** (FR-A7). Тест: блок, чей ответ отвергнут, не может
   попасть в документ ни в маркерном, ни в немаркерном режиме.
6. **Немаркерный переспрос не создаёт и не уничтожает абзацы.** Число абзацев блока до и после
   ступени 2 совпадает; при делении по предложениям куски склеиваются обратно в текст ТОГО ЖЕ абзаца.
7. **Ни один отказ по качеству текста на абзаце ПРОЗЫ не имеет решения `fallback_continue`.** Прямой
   тест над `classify_processed_block_failure_decision:140-167`: для каждого из семи качественных
   видов (`block_execution.py:21-27`) на прозаическом абзаце решение не равно `fallback_continue`.
8. **Анти-вакуум инварианта: на АППАРАТЕ `fallback_continue` сохраняется.** Правило, отказывающее
   всем, сломано ровно так же, как правило, разрешающее всем. Тот же тест на абзаце из региона
   сносок / оглавления / индекса обязан вернуть `fallback_continue`. Десять структурных видов
   (`:28-37`) остаются `fail` — их эта работа не трогает.
9. **Лестница завершается.** Ступень 4 не может вызвать саму себя, и число вызовов модели на один
   блок ограничено сверху (FR-A6). Тест на подставном клиенте, который всегда отказывает: вызовов
   конечное число, и оно вычислимо из числа абзацев блока.
