Короткий front-door для ИИ-агентов и automation. Здесь только правила и маршрутизация; подробности живут в специализированных документах и линкуются отсюда.

**Как читать этот файл.** Правила ниже сформулированы как обязательства, а не пожелания. Почти каждое написано после конкретной ошибки — где инцидент известен, он назван с датой. Правило с историей переживает редактуру; голый императив выбрасывают при первой чистке.

## 1. Источник правды — код и git, а не документы

**Правило: если этот файл противоречит `git log`, прав `git log`.**

Документация дрейфует месяцами. Типовой провал: агент строит план из датированного roadmap, читает «следующий шаг — X» и предлагает работу, сделанную месяц назад.

Перед любым планированием:

```bash
git branch -r --sort=-committerdate     # есть ли ветки новее main без PR?
gh pr list --state all
git log --oneline main --grep="<маркер задачи>"   # реальный статус, а не поле Status:
```

Ветка, запушенная без PR, — худший случай: CI по ней не проходил, ревью не было, а `main` о работе не знает.

**Не храните в документах значения, которые протухают.** Вместо значения храните команду, которая его выдаёт. Три случая:

1. Значение меняется при каждом слиянии (текущий HEAD, «N тестов проходит») → **храните команду, а не число**.
2. У значения есть законный владелец в репозитории → **храните указатель на владельца**, а число живёт там (см. храповик, §7).
3. Утверждение не сводится к команде («владелец решил так-то») → **обязательно с датой**. Дата — сигнал: чем старше, тем внимательнее перепроверяйте.

Исключение: хеши как исторический факт («фича приехала в `58aaf2a`») — нормально и полезно. Прошлое не протухает. Запрещено только «вот здесь ветка находится сейчас».

## 2. Canonical path vs debug path

Единственное различие, которое чаще всего решает, честен отчёт агента или нет.

- **Canonical path** — тот entrypoint, которого требует репозиторный контракт или сам тестовый selector: `<канонический раннер>`, `<скрипты валидации>`, соответствующие задачи редактора.
- **Debug path** — любой обходной запуск для локальной диагностики: прямой вызов раннера, ad-hoc однострочник, внутренний helper.

Правила:

- Если requested selector сам завязан на shell-bound contract, debug path **не является доказательством** его выполнения — он подтверждает только внутреннюю гипотезу.
- **Нельзя подменять canonical path на debug path молча.** Маркируйте такой запуск как `debug-only`.
- Если canonical path недоступен — **сообщите именно это ограничение**, а не пишите, что тест выполнен «эквивалентно другим способом».
- Принятие debug-only прогона как достаточного — это решение пользователя, а не агента.

## 3. Runtime и окружение

Канонический runtime проекта: `<runtime>`. Для тестов, диагностических импортов и проверки зависимостей источником истины считается он.

- **Определяйте окружение фактически, а не по предположению.** Первой командой выясните, где вы находитесь (`uname`, `pwd`, фактические пути к исполняемым файлам).
- **До любого вывода «env сломан» проверьте фактические executable paths.** Если реальный layout расходится с ожидаемым — зафиксируйте это как состояние workspace и выберите рабочий путь, а не объявляйте тесты незапускаемыми.
- **Deterministic readiness check.** Одна короткая локальная проба без сети, с *закрытым списком* того, что считается блокером. Если проба прошла — **прекращайте исследовать окружение и запускайте requested команду**. Без закрытого списка агенты уходят в бесконечную разведку.

```bash
<команда-проба ... && echo READY>
```

Блокером считается только: `<перечислить исчерпывающе>`.

## 4. Канонические команды

```bash
<раннер тестов> <selector>        # тесты
<команда линта/типов>             # статические проверки
<команда сборки/запуска>          # запуск приложения
```

Канонический раннер должен **отказываться от неоднозначных вызовов громко**: неверный selector, чужое окружение, аргументы в неправильном порядке. Молчаливый неверный запуск даёт не ошибку, а *правдоподобно выглядящий ложный результат* — «0 тестов собрано» читается как успех.

Он же должен **предупреждать о грязном рабочем дереве**: CI всегда идёт на чистом checkout'е, и «локально проходит, на CI падает» рождается именно здесь.

## 5. Прежде чем сказать «готово»

**BINDING-чеклист.** Написан после того, как ревьюер дважды нашёл реальные дефекты после объявления работы завершённой.

Корневая причина обоих случаев одна: **проверялся механизм («мой код делает X»), а не эффект («X действительно меняет результат на каждом достижимом пути»)**.

1. **Перечислите все call-site.** Изменили функцию или параметр — найдите grep'ом **каждого** вызывающего и убедитесь, что он попадает на исправление. Никогда не проверяйте только тот путь, который трогали.
2. **Пройдите все достижимые пути** перед утверждением уровня класса: синхронный, фоновый, restart/fallback, попадание и промах кэша. **Ограничивайте заявление тем, что реально проверили**: «закрыто для пути X, проверено Y; пути Z не проверялись» — никогда не глухое «полностью закрыто».
3. **Проверьте эффект, прогнав реальный сквозной путь**, а не чтением диффа и не узким юнит-тестом. Тест на «действительно ли это блокирует/гейтит?» пишется **первым**, включая неудобные режимы.
4. **Adversarial-проход** отдельным шагом или отдельным агентом, чья единственная задача — найти пропущенное: братья того же бага, непройденные ветки, общее состояние (кэши, глобалы), которое игнорирует новый параметр.
5. **Проверьте CI после пуша.** Локально зелёное ≠ CI зелёное. Если авторизация не работает — **сообщите это как блокер**, а не пропускайте молча.
6. **Закройте контур доказательств** в той же волне: статус спеки → с SHA коммита и фактическим результатом прогона. Никаких висящих «прогон будет позже».
7. Для следующего раунда ревью **начинайте новую сессию**: длинный сжатый контекст измеримо ухудшает внимание и заставляет доверять собственным сводкам вместо кода.

## 6. Evidence-дисциплина

- **Доказательство должно быть свежее исправления.** Утверждение «дефект живой» опирается на свежий прогон или детерминированный тест против текущего кода. Сохранённые фикстуры и отчёты доказывают только то, что было верно на момент их снятия. Прежде чем заявлять живой дефект по сохранённому артефакту, сравните дату артефакта с историей кода, который он описывает.
- **Критерии приёмки перепроверяются заново, когда меняется описываемый ими код.** Критерий, который больше нельзя удовлетворить, — это дефект спеки, а не пробел реализации. (Инцидент: критерий, написанный по фикстурам старше исправляющего коммита, застопорил ветку на неделю, пока агенты пытались заставить корректный код его удовлетворить.)
- **Никаких гипотез из памяти сессии.** До любой гипотезы: прочитать свежий отчёт, **дословно процитировать провалившиеся проверки** с парой `actual`/`threshold`, и только потом рассуждать.
- **Зелёная метрика — не доказательство.** Откройте фактический результат и посмотрите на него. Метрики скрывали реальные дефекты до тех пор, пока артефакты не открывали руками.
- **Отсутствующее измерение должно отличаться от нулевого.** Иначе «ноль потерь» выглядит как идеальный результат.
- **Аудируйте ту стадию, которая владеет дефектом**, а не ту, до которой удобно дотянуться. Исправление в стадии X не чинит дефект, рождённый в стадии Y. Дешёвая изолированная диагностика одной стадии лучше дорогого сквозного прогона.
- **Дорогой сквозной прогон — это веха, а не шаг отладки.**
- **Не связывайте в один слайс независимые провалы с разными корневыми причинами.** Каждый класс — отдельный мини-план.

## 7. Механизм храповика (ratchet)

Для любой метрики с монотонным направлением (число ошибок типов, покрытие, размер бандла, список известных падений):

- Эталон — **константа в тесте**, а не число в документе.
- Тест падает **и при ухудшении, и при неучтённом улучшении** («стало лучше — обновите константу»). Улучшение всегда разрешено, но должно быть *записано*, иначе эталон тихо уползает выше реальности и заново впускает долг.
- **Версия инструмента закреплена**, замер делается **на чистом дереве**, область проверки ограничена собственным кодом — иначе число пляшет между локалью и CI.
- Каждое движение эталона — **датированная строка с причиной** и с честной пометкой, расчищен долг настоящими исправлениями или подавлениями.

Именно двусторонность делает безопасной ссылку на константу вместо цитирования числа: разойтись с реальностью она не может.

## 8. Спеки: два уровня

- **Только спека — нормальный случай.** Работа по конкретной находке, следствия ревью, измерения, отрицательные результаты, решения. Объём уже ограничен породившей её находкой, а проверка — прогоном тестов.
- **Спека → план → задачи → реализация** — только когда работа вводит новый модуль или контракт, затрагивает несколько модулей, где важен порядок изменений, либо имеет альтернативы дизайна, о которых стоит спорить до написания кода.
- Когда уровень неочевиден — **спросите владельца. Угадывать «полный цикл» не является безопасным выбором по умолчанию**: это тратит бюджет ревью на бумагу, которую спека уже покрыла.
- **Никогда не пишите план или задачи задним числом.** План, созданный после кода, ничего не документирует и вводит следующего читателя в заблуждение о том, как принималось решение. Лекарство для завершённой работы — запись в Changelog спеки, а не реконструированный план.

**Не применяйте процесс спек к:** узким исправлениям с очевидным ожидаемым поведением, прямым просьбам прогнать тесты или диагностику, правкам форматирования, точечным обновлениям ожиданий в тестах.

Правило, объясняющее сам двухуровневый режим: **правило, которого никто не соблюдает, ничего не защищает — оно лишь порождает ложные находки, когда кто-то проводит аудит по нему.**

### Где живут спеки

- `specs/<NNN>-<slug>/` — одна единица работы. Всегда `spec.md`; `plan.md` и `tasks.md` — только на полном цикле. **Папка, в которой лежит только `spec.md`, — нормальная форма, а не незавершённая.**
- Историческим планам и датированным документам отведите отдельное место и **закройте его для новых записей**. Два хранилища спек не взаимозаменяемы: как только новые спеки начинают появляться среди исторических, статус работы перестаёт быть определимым.

### Шапка спеки

```markdown
# <Тип>: <краткое название>

Date: <дата создания>
Status: <СТАТУС> (<дата>). Коммит `<sha>`. Доказательство: `<selector>` PASSED
        (<фактический результат прогона, время>). Статус-строки не авторитетны —
        см. Changelog ниже и `git log` по owner surface.
Owner surface: `<модуль, который владеет дефектом>`
Companion / Supersedes: `<ссылки на связанные спеки>`
```

- **`Status` пишется вместе с доказательством**, а не одним словом: SHA коммита, фактический результат прогона, дата. `IMPLEMENTED` без прогона — это обещание, а не статус.
- **Шапка обязана признавать собственную неавторитетность** и отправлять читателя к `git log`. Наши статус-строки отставали от кода месяцами; спека, которая честно об этом предупреждает, не вводит следующего читателя в заблуждение.
- **`Owner surface`** — модуль, который владеет дефектом. Прямое следствие §6: исправление в стадии X не чинит дефект, рождённый в стадии Y, и спека должна называть правильную стадию до того, как кто-то начнёт чинить удобную.
- **Отложенная работа помечается с причиной и с явным «сам не поднимай»**: «заблокировано материально, а не по приоритету: нужен `<X>`, которого у владельца нет». Спека остаётся открытой, чтобы вопрос был виден в навигационном документе, а не тихо забыт.

### Обязательные разделы

- `## Problem` — с датой проверки **каждой** причины и ссылками `path/file.py:line`. Если причина позже переосмыслена, это фиксируется тут же пометкой «причины перепроверены и исправлены `<дата>` — см. Changelog», а не переписыванием истории.
- `## Non-goals` — что работа сознательно **не** делает, и почему. Без этого объём расползается в бесконечную полировку.
- `## Anti-regression` — инварианты, которые обязаны выжить, и контрпроверка для каждого правила, что-либо списывающего (§9, anti-vacuum).
- `## Changelog` — дописывается каждый раз, когда находка или критерий исправлены. Это же единственное честное лекарство для завершённой работы, которой не хватает плана: запись в Changelog, а не реконструированный задним числом план.

### Известно-открытое внутри закрытой спеки

Если при закрытии обнаружено смежное, но отдельное — выносите его в явный блок `KNOWN-OPEN (сознательно вне этой спеки)` с описанием и указанием, где это отслеживается. Это то же правило, что и §5.2: заявление ограничивается тем, что реально проверено. Молча закрытая спека с несобранным хвостом — это будущая находка ревьюера.

### Когда пора выносить конституцию отдельным файлом

Пока проект один и агент один, **держите все правила здесь**. Два документа с правилами — это поверхность для противоречий, а противоречие не даёт ошибку: оно даёт молчаливый произвольный выбор. У нас именно так и вышло — секция входного файла требовала план безусловно, что прямо противоречило принципу о двух уровнях, и агент мог удовлетворить один контракт или другой, но не оба.

Выносите конституцию, когда выполнено хотя бы одно:

- **появился второй потребитель правил** — второй ассистент со своим входным файлом или человек-контрибьютор: дублировать правила по файлам значит гарантировать дрейф, и нужен нейтральный корень, на который ссылаются все;
- **правило понадобилось менять с записью** о том, что было раньше и почему сломалось: тогда нужны версия и журнал изменений, а не тихая правка.

Если выносите:

- каждый принцип — **MUST плюс отдельный абзац «почему»**, и по возможности с датой инцидента, который его породил. Принцип без истории выбрасывают при первой чистке;
- версионируйте по semver: **MAJOR — принцип убран или переопределён, MINOR — добавлен принцип или раздел управления, PATCH — уточнение формулировки**;
- держите наверху журнал изменений с переходом версий и списком документов, которые надо синхронизировать;
- **помечайте неутверждённое как неутверждённое.** Пока владелец не подписал изменение, пишите прямо: описание текущей практики считается точным, само правило — предварительным, и если от него зависит реальное решение — спрашивайте, а не ссылайтесь на документ. Выдавать черновик за закон дороже, чем признать его черновиком.

Не пишите конституцию в первый день проекта. Она работает ровно настолько, насколько каждый её принцип — это шрам с датой; те же слова, написанные авансом, — благие пожелания, которые никто не соблюдает.

## 9. Правила изменения кода

- **Универсальные правила вместо литералов под конкретный случай.** Детект опирается на структурную роль или форму, а не на список слов, счётчик сигналов или строку, взятую из одного входа. **Дефект, для которого нет общего правила, ПРИНИМАЕТСЯ, а не патчится**: редкие хвосты качества — осознанный исход, а не бэклог. Тюнинг под конкретный вход не переносится на следующий, раздувает код и прячет реальные потери за правдоподобными исключениями.
- **Нет сигнала в источнике — нет починки.** Не восстанавливайте смысл из формы (позиция, длина, регистр, ведущий номер). Честные варианты: починить стадию выше, чтобы сигнал появился, либо принять дефект. **Никогда не угадывайте в сборщике.**
- **Anti-vacuum: любое правило, которое что-то списывает или исключает, обязано нести контрпроверку**, показывающую, что реальные случаи всё ещё считаются. Гарды, проходящие вхолостую, — типовой способ получить ложное зелёное.
- **Наличие содержимого ≠ наличие формы.** Не засчитывайте покрытие, если текст выжил, а его структурная роль потеряна.
- **Данные для ревью ≠ гейт вердикта.** Метрика, выведенная человеку для осмотра, не должна становиться жёстким провалом.
- **Минимальные изменения в границах задачи.** Никаких попутных рефакторингов. **Существующие изменения пользователя в рабочем дереве обязаны быть сохранены.**
- **Никакой опоры на компенсацию ниже по потоку.** Запрещённые рассуждения: «это безопасно, потому что потом всё равно сработает fallback»; «валидатор можно ослабить, дальше разберётся мягкий приём». **Каждый этап обязан быть корректным сам по себе.**
- **Нарушение целостности — это гейт, а не строчка в логе.** Если рассогласование делает корректную сборку невозможной, выберите явное действие: прервать с внятной ошибкой, откатиться к безопасному варианту, сохранить оригинал или явно пометить результат деградированным. Молча продолжать нельзя.
- **Не выдавайте эвристику за ИИ.** Если функция не вызывает модель, так и называйте её. Нейминг и комментарии не должны завышать реальную надёжность.
- **Каждый внешний вызов ненадёжен по умолчанию**: таймаут, ретраи, backoff, раздельная обработка временных и политических отказов, логирование причины fallback. Схема `call → except Exception → fallback` без разбора классов отказа запрещена.
- **Если это можно протестировать без UI — оно не должно рождаться в слое UI.**

## 10. Защищённые контракты

Список поверхностей, которые меняются **только намеренно**: `<раннер тестов>`, `<конфиг задач>`, `<сторожевые тесты>`, `<манифесты зависимостей>`.

- Запрещено трогать их в рамках несвязанной задачи.
- Если пользователь просит изменить контракт — меняйте **одним согласованным набором**: код + конфиг + сторожевой тест + документация, затем прогон сторожевого теста и полного набора.
- Цель: **контракт должен ломаться только намеренно, обзорно и с явным обновлением всех уровней источника правды.**

**Качество тестов — тоже защищённый контракт.** Без явной просьбы не добавляйте:

- тесты, проверяющие, что документ содержит определённые заголовки или формулировки, вместо поведения продукта: если тест может упасть из-за редакторской правки документации, а не из-за регрессии приложения, ему не место в основном наборе;
- тесты «тонкой проводки», подтверждающие лишь, что обёртка вызвала внутреннюю реализацию с теми же аргументами, без проверки наблюдаемого эффекта.

Приоритет: пути успеха и отказа пользователя, переходы состояний, реальные выходные артефакты, реальные контракты гардов.

**Гард проверяет форму, а не истину.** Автоматизируйте тот дрейф, который реально случился, и прямо пишите в докстроке, что судить о правдивости прозы тест не берётся — гард, притворяющийся обратным, и есть ложное зелёное. **Сообщение об ошибке — это документация**: оно должно называть, что сделать вместо этого, и команду, которая решает, какой из вариантов верен.

## 11. Наблюдаемость и артефакты

- **Фича не завершена, если её результат нельзя найти, продиагностировать и проверить.**
- Один центральный канал логирования, один формат записи, один источник уровня логирования. Прямое использование системного логгера в продовом коде запрещено.
- **Каждая пользовательская ошибка несёт идентификатор для корреляции** — чтобы сообщение из интерфейса можно было найти в логе.
- Имена событий — глобально уникальные, читаются как «что произошло», без синонимов для одного и того же значения.
- **Не логируйте** секреты, токены, полные промпты и ответы моделей (только усечённый превью и счётчики), не логируйте в каждой итерации цикла отрисовки.
- **У каждого семейства артефактов есть TTL и лимит числа**, объявленные константами в единственном модуле политики; чистка вызывается сразу после записи. Runtime-артефакты отделены от версионируемых фикстур, и чистка никогда не трогает фикстуры.
- **Корень репозитория — не свалка артефактов.** Не легитимизируйте мусор добавлением новых ignore-правил.
- **Отказ пост-доставочного шага не должен отменять уже доставленный результат.**
- Когда вы поставляете инструмент, проверяющий правило, **задокументируйте, чего он не видит** — чтобы его молчание не принимали за доказательство.

## 12. Работа с агентами и независимое ревью

- **Независимую, непересекающуюся работу — исследование, ревью, разработку — отдавайте субагентам**; главная сессия остаётся оркестратором, держащим контекст. Параллельные агенты не должны править одни и те же файлы.
- **Проверяйте несущие факты, которые вернул агент, прежде чем действовать.** Агенты ошибаются: перепроверьте инвентаризацию, названную «полной», прочитайте код за утверждением «изменений в поведении нет», убедитесь, что процитированный `file:line` существует.
- Правила из §5 (перечислить call-site, пройти все пути, adversarial-проход) кладите **в промпт каждого агента-разработчика**.
- В промпт агента всегда включайте блок «как запускать» — иначе он переоткрывает это каждую задачу.
- **После крупной пачки работы — независимое ревью другой моделью/CLI**, не после каждой задачи. Оно ходит другой моделью и видит то, чего не видит внутренний цикл. Измеренный результат: шесть реальных находок в работе, уже прошедшей три собственных adversarial-раунда, включая тест анти-регрессии, который проходил вхолостую.
- **Каждую внешнюю находку проверяйте сами перед исправлением**: одна из шести оказалась слабее заявленного, а первая попытка починить главную нарушила собственный принцип «никаких литералов под случай».

## 13. Честный учёт долга

Разделы, которые обязаны существовать и обновляться, иначе документ перестаёт быть достоверным:

- **«Что открыто»** — с причиной, почему открыто, и что разблокирует.
- **«Принятые потолки — не переоткрывать»** — решения, закрытые владельцем осознанно и с цифрами, с явной пометкой «сам не поднимай». Это то, что останавливает бесконечное перерешивание.
- **«Зарегистрировано, но не описано»** — имена и сущности, занятые в коде, но пока без описания; выдумывать семантику по имени — ровно то враньё документации, против которого написан документ.
- **«Чем это НЕ является»** — прямо назвать документы, которые утверждают обратное, и пометить их историческими.
- Решения владельца **терминальны и датированы**.

Меряйте в единицах, которые ощущает пользователь, сообщайте «до/после» вместе со стоимостью и временем, разбивайте результат по операциям и **прямо говорите, когда результат не обобщается**.

## 14. Запрещено

- Планировать по датированным документам и полям статуса вместо `git log`.
- Выдавать debug path за выполнение canonical path.
- Заявлять «всё зелёное» без проверки чистоты рабочего дерева.
- Объявлять прогон CI успешным или упавшим, пока у него нет финального состояния.
- Трактовать оборванный вывод как результат теста: **частичный вывод — это сначала проблема транспорта, а не вердикт**. Сужайте selector, а не расширяйте прогон; один активный прогон на одно расследование.
- Утверждать что-либо о текущем поведении без ссылки `file:line` в свежем артефакте.
- Называть проваленную проверку «косметикой» или «не блокером» без явного разрешения владельца.
- Заявлять, что окружение сломано, не проверив фактические пути.
- Смешивать текущее состояние и целевую архитектуру без явной маркировки. Неподтверждённое утверждение помечается как гипотеза или риск, а не как факт.
