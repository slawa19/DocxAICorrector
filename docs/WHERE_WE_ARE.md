# Где мы сейчас

**Обновлено: 2026-08-01.**

## Как читать этот файл

Это **навигация, а не источник правды**. Источник правды — код и `git`. Документы в этом
репозитории уже один раз соврали дорого: сессия 2026-07-31 начала планирование с
`docs/specs/GLOBAL_PLAN_2026-06-16.md`, прочитала там «дальше — UI-слайс» и предложила владельцу
делать UI, который на самом деле был сделан и влит месяцем раньше (спека 013). Поэтому здесь нет
пересказа состояния — здесь команды, которыми состояние проверяется за десять секунд, и список
мест, где документация уже расходилась с реальностью.

Правило: **если этот файл противоречит `git log`, прав `git log`.** Если заметили расхождение —
поправьте этот файл тем же PR, в котором заметили.

### Почему здесь нет ни хеша текущего `main`, ни чисел тестов

Первая редакция этого файла (2026-07-31) начиналась строкой «`main` = такой-то хеш» и приводила
здоровье проекта числами вида «столько-то тестов прошло». Через сутки оба утверждения были ложными:
их опроверг первый же влитый PR. Документ, написанный против устаревания документации, устарел за
день — и ровно тем способом, от которого он должен был защищать.

Вывод, который здесь и зафиксирован: **значения, меняющиеся при каждом слиянии, в этом файле не
хранятся вообще.** Вместо значения хранится команда, которая его выдаёт (следующий раздел). Если у
числа есть законный владелец в репозитории — число живёт у владельца, а сюда попадает только ссылка
на него: эталон pyright, например, это константа `_ERROR_BASELINE` в `tests/test_typecheck.py`, и
тест падает и при её превышении, и при снижении, так что разойтись с реальностью она не может.

Исключение — хеши, названные как исторический факт: «UI влит коммитом `58aaf2a` 2026-07-13».
Прошлое не протухает, и такие ссылки полезны.

Утверждения о состоянии, которые нельзя свести к команде («владелец принял такое-то решение»),
всегда идут с датой. Дата — сигнал читателю: чем она старше, тем внимательнее перепроверяйте.

Гард `tests/test_where_we_are_freshness.py` не даёт вернуть сюда счётчики тестов и приколоченный
хеш `main`. Он ловит именно ту форму дрейфа, что случилась, и ничего больше — оценивать
осмысленность прозы автоматика не умеет, это остаётся на ревью.

## Проверить состояние: команды вместо чисел

Всё запускается **только в WSL**. `scripts/test.sh` из Git Bash под Windows подхватывает системный
Python и даёт ложные падения.

```bash
git log --oneline -5 main                        # что влито последним
bash scripts/test.sh tests/ -q                   # полный набор тестов
bash scripts/test.sh tests/test_typecheck.py -q  # храповик pyright: падает и при росте, и при снижении числа ошибок
bash scripts/run-real-document-quality-gate.sh   # канонический гейт реальных документов, четыре книги корпуса (~15 минут)
```

## Проверить статус любой спеки

Не читайте поле `Status:` в `specs/NNN-*/spec.md` как истину — оно исторически отставало на месяцы.
Проверяйте так:

```bash
git log --oneline main --grep="spec 043"       # есть ли работа по спеке в main
git merge-base --is-ancestor <commit> main     # влит ли конкретный коммит
git log --oneline main..<branch>               # что есть в ветке и ещё не в main
```

Статусы спек 012–051 были выверены и приведены в соответствие 2026-07-31. Если вы читаете это
сильно позже — перепроверьте, дрейф возобновляется.

## Что открыто

**Спека 050 — двухколоночные PDF. ОТЛОЖЕНО решением владельца 2026-07-31, без даты. Не поднимать
самостоятельно.** Ревью раунда 10 (находка F6) утверждало, что двухколоночные PDF читаются
вразнобой, но это вывод из чтения кода, а не из прогона: корпус состоит только из одноколоночных
книг. Проверить это нечем — **у владельца нет двухколоночного PDF**. Двухколоночный документ, с
которым он работал, — это DOCX, а он идёт совсем другим путём импорта и на вопрос спеки ответить не
может. Поэтому вопрос припаркован: ничего не реализуем, ничего не планируем, но и не забываем — если
однажды появится настоящий двухколоночный PDF, начинать с раздела «Decision plan» в спеке. Спека
намеренно оставлена со статусом `DEFERRED` (то есть открытой), чтобы гард продолжал требовать её
упоминания здесь. Почему нельзя «просто починить по коду»: спека 049 ровно так и кончилась — идею
реализовали по безупречной трассировке кода, замерили (0 восстановленных заголовков, 1 потерянный) и
откатили.

**Первый боевой прогон читательской вычитки ещё НЕ сделан** (спека 052 — подготовка к нему —
закрыта 2026-07-31). Проход был мёртв в интерфейсе до спеки 047, поэтому в проде не работал ни разу.
Главное, что выяснилось при разборе: **проход физически не может переписывать формулировки** — все
его операции либо удаляют блок, либо переставляют текст, который уже есть в исходнике, со сверкой
символов. Это структурный уборщик, а не редактор; «полировать формулировки» им нельзя никаким
промптом. Перед прогоном закрыты девять пунктов (включая настоящую причину давней потери картинок),
операция смены роли удалена. **Что осталось сделать перед самим прогоном:** договориться о критериях
успеха (раздел «Define success before spending the book» в спеке) и вернуть
`DOCX_AI_READER_CLEANUP_ENABLED=true` — 2026-07-31 он выставлен в `false`, чтобы проход не включился
сам собой как побочный эффект слияния.

**Спека 017 — штампы и грифы на сканах.** Единственная реально открытая спека из старого пласта,
статус `BACKLOG` честный. Повторяющийся на каждой странице штамп («Секретно», «Для служебного
пользования») не распознаётся как страничная «мебель» и переводится как обычный текст, десятками
повторов. Точки вставки известны и указаны в спеке; тестов на этот класс сейчас нет.

**Осознанно оставленный долг раунда 12** — перечислен в
[`specs/051-round12-premerge-remediation/spec.md`](../specs/051-round12-premerge-remediation/spec.md),
раздел «Not fixed here — deliberate residue». Это четыре мелких дефекта (P3), каждый с указанием
места; ни один не блокирует. Два вопроса, которые тот же раздел адресовал владельцу, с тех пор
решены: локальный `.env` переведён на `DOCX_AI_READER_CLEANUP_ENABLED=false`, а потерю коротких
заголовков на PDF-книгах владелец принял как потолок PDF-входа — см. следующий раздел.

**Часть тестов не выполняется в CI никогда.** `.github/workflows/ci.yml` снимает маркеры
`system_deps`, `manual_ai_heavy` и `browser_ui` и ставит `DOCXAI_SKIP_WORKFLOW_SMOKE=1`. Причина
законная — на раннере нет LibreOffice и браузера, а часть тестов ходит в платные модели, — но
покрытием это не становится. Сколько тестов выпадает по маркерам, покажет

```bash
bash scripts/test.sh tests/ -q --collect-only -m "system_deps or manual_ai_heavy or browser_ui"
```

плюс те, что пропускает переменная `DOCXAI_SKIP_WORKFLOW_SMOKE`. Отдельная задача со статическими
проверками (`-m static_workflow`) здесь ни при чём: с 2026-07-31 она выбирает тесты по маркеру, а не
по списку файлов, поэтому новый файл с этим маркером выпасть из CI больше не может.

## Принятые потолки — не переоткрывать

Здесь лежат вопросы, по которым решение уже принято владельцем. Каждый закрыт не «руки не дошли», а
осознанно, с цифрами. Если возникает соблазн предложить по ним улучшение — сначала прочитайте спеку.

**Короткие заголовки на книгах из PDF теряются, и это потолок PDF-входа** (решение 2026-07-31, спеки
[046](../specs/046-universal-short-heading-evidence/spec.md),
[049](../specs/049-pdf-import-preserves-font-size/spec.md),
[053](../specs/053-short-heading-evidence-measurement/spec.md)). Замерено дважды. Размер шрифта не
различает ничего: ни один из 30 потерянных заголовков не имел шрифта крупнее соседей — поэтому
спека 049, которая пыталась протащить размер шрифта, дала ноль. КАПС — анти-признак, он втрое чаще
встречается у мусора. Различает только асимметрия вертикального отступа и контраст
жирность/курсив/центрирование, но продовый импорт PDF записывает в промежуточный DOCX **лишь жирность
и курсив**, так что на реальном PDF от правила остаётся треть. Когда структура важна — подавать книгу
в DOCX, там типографика сохраняется полностью. Новых эвристик по заголовкам не предлагать.

**Двухколоночные PDF** — см. раздел «Что открыто»: вопрос припаркован, потому что проверить его не на
чем.

## Как обновлять этот файл

Тем же PR, который меняет положение дел. Если PR закрывает спеку, меняет направление или добавляет
известный долг — правка сюда входит в его объём. Файл должен оставаться коротким: он навигация, а
не летопись. Историю ведут `git log` и `CHANGELOG.md`.

И не возвращайте сюда числа, которые протухнут: вместо «столько-то тестов зелёные» пишите команду,
которой это проверяется, вместо «`main` сейчас такой-то» — ничего, потому что это и так покажет
`git log`.
